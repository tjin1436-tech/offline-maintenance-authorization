# 关键恢复机制消融实验：Linux 参考结果

本批已实际完成 36 组运行（3 个版本 × 4 个场景 × 3 次重复），包含 27 次网关强制终止。数据库、签名和 EVM 交易交叉核验通过，33 条链上记录对应 66 笔登记与提交交易。5 项篡改负对照均被审计拒绝；另用 Python sqlite3 复算 36 组的 8 个数据库指标，与 Node 审计输出一致。

本批环境为 linux / Node v24.19.0 / AMD EPYC 9V74 80-Core Processor。它是新取得的 Linux 参考证据，不是此前 Windows Stage 6 批次，也不是用户 Windows Stage 7 已完成的结果。Windows 复现请运行本包的 run_windows.bat；结果需单独报告。

## 主要结果

下表每行汇总该版本的 12 组运行（包括无故障控制）；计数不是随机故障发生率。

| 版本 | 配额超用数量 | 同标识重复效果 | 缺失网关操作记录的效果 | 最终 PENDING | 原始 op1 完成 |
|---|---:|---:|---:|---:|---:|
| 完整版本 full | 0 | 0 | 0 | 3 | 9/12 |
| 延后预留 late_reserve | 3 | 0 | 3 | 0 | 6/12 |
| 直接重试 retry_pending | 0 | 0 | 0 | 0 | 12/12 |

1. **执行前持久化预留与意图记录有具体作用。** 在 after_effect 场景中，late_reserve 的 3/3 次运行均在机器人完成 op1 后丢失网关意图，重启后又接受同授权下的 op2。授权配额为 1，但每次产生 2 个不同操作的模拟效果。完整版本 3/3 次均恢复 op1 并拒绝 op2。这里发生的是两个不同操作造成的配额超用，不是同一个操作重复执行。
2. **完整版本的保守恢复确有可用性代价。** 在 before_dispatch 场景中，完整版本的 3/3 次运行均保留已预留的 PENDING，机器人没有产生效果；一次回执核实仍未找到证据，后续操作被阻塞。这不是实验运行失败，而是该恢复规则的实际行为。
3. **直接重试在本执行器假设下表现更好。** retry_pending 在 before_dispatch 的 3/3 次运行完成了原 op1；在 after_effect 与 during_done 的 6 次运行中，重发带来 6 次额外 execute 调用，但持久化去重阻止了重复效果。它在本矩阵中没有配额违规、证据缺失或最终 PENDING。不能把重试请求数当成实际执行数。
4. **切点决定延后预留是否暴露问题。** during_done 场景中，late_reserve 的预留事务已经提交，完成事务中断后能够凭回执恢复，因此这 3 次没有相同违规。无故障条件下三个版本均按配额完成一项操作并拒绝后续不同操作。

## 可写入论文的结果表述

为检验执行前持久化与恢复策略的作用，本文在统一原型中比较完整版本、延后预留版本和未知结果直接重试版本。三个版本共享签名验证、机器人持久化去重、完成事务及登记合约。在 Linux 参考批次中，四个受控场景各重复三次，共完成 36 组运行。在机器人完成而网关尚未持久化预留的切点，延后预留版本三次均产生单授权配额超用，并各遗留一项缺少网关操作记录的已执行效果；完整版本保持配额约束并恢复完成证据。另一方面，完整版本在发送前终止的三次运行中均保持 PENDING，直接重试版本则利用机器人端持久化去重完成原请求，且在所测场景中未产生重复效果。结果说明执行前预留与意图记录能阻止本实验所示的跨崩溃配额失记；未知结果的恢复选择则取决于执行器是否提供可靠去重与结果查询，保守等待并非在所有执行器条件下都具有更高可用性。

以上段落只适用于本 Linux 批次。若采用 Windows 批次，须依据其原始结果重新核验和替换环境与数值，不预设跨平台结果相同。

## 对研究贡献的影响

可加强的主张：执行前持久化预留与意图记录、独立回执、恢复后登记形成可核验的约束链；消融给出其在特定故障窗口的作用及代价。

需避免的主张：禁止重试必然优于重试；PENDING 本身保证物理动作恰好一次；三个版本的样本量能够估计生产失败率；链上存在一致记录即可证明没有漏记的机器人效果。late_reserve 的反例恰好说明，机器人回执与网关证据必须交叉核对。

该消融一次移除“执行前配额预留 + PENDING 意图”组合，尚未分别归因于二者。真实机器人、执行器去重失效、授权过期、在线撤销、跨主机网络与长期稳定性仍未验证。本阶段没有评估延迟或吞吐，也未比较区块链和集中式数据库。
