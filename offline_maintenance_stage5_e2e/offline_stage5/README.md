# 第五阶段：本地 HTTP、签名与 EVM 端到端实验

## 在 VS Code 中运行

解压 `offline_maintenance_stage5_e2e.zip`，用 VS Code 打开 `offline_stage5` 文件夹，继续使用第三阶段已经安装的 Node.js 24。依赖版本沿用第三阶段：ethers 6.13.5、Ganache 7.9.2、solc 0.8.28。无需 Python、真实机器人或手动启动 Ganache。

在终端依次执行：

```powershell
npm ci
node run_benchmark.cjs --repeats 3 --output stage5_results
node audit_benchmark.cjs --input stage5_results
node test_audit.cjs --input stage5_results
```

`npm ci` 需要联网下载依赖；若下载失败且保留了第三阶段工程，可将其完整 `node_modules` 文件夹复制到第五阶段同名目录，依赖版本相同。程序自动选择本机空闲端口，启动和关闭本地开发链及 HTTP 服务；正常运行需数分钟，耗时取决于电脑。默认矩阵为 3 次重复 × 2 种注入延迟 × 3 种网络场景 × 3 种授权策略，共 54 组、324 次命令请求。运行程序不预设离线命令全部成功；超过期限时拒绝请求是正确行为。

预期：最后显示 `Completed runs: 54`；审计 `audit_success: true`；负对照报告 `positive_control_passed: true`，四项 `rejected: true`。若出现异常，请保留终端输出和结果文件，不要删除失败记录后宣称全通过。重跑应使用新的非空目录之外的路径，如 `--output stage5_results_rerun`。

实验完成后压缩并上传：

```powershell
Compress-Archive -Path .\stage5_results -DestinationPath .\stage5_results.zip
```

参考文件夹 `verified_stage5` 是作者环境下的一次重复、18 组实测记录，用于复现核对，不代表你电脑的性能。请上传本机生成的 `stage5_results`，不要上传参考文件夹。本阶段开发链采用内存数据库。程序在原节点退出前查询全部回执与记录，审计随后在新节点重放相同注册与提交调用，核对事件和合约状态；这不是原链重启持久化验证。

## 实验实际做了什么

维修人员客户端签名请求 → HTTP 网关验证 → HTTP 机器人接口模拟器返回签名确认 → 网关签名执行记录并同步写入磁盘 → 重连后可信桥校验 → 本地 EVM 注册授权并提交记录 → 获得真实交易回执。

授权服务、网关、机器人接口和两个外部连接代理使用真实本机 HTTP。外部连接代理同时控制授权服务与 EVM RPC 的可达性；机器人本地接口保持可达。控制器直接设置的是测试代理状态，网关只通过 HTTP 心跳获知连接变化，没有直接读取故障开关。

HTTP 服务共享同一个 Node.js 进程，Ganache 是独立子进程；它们不是多机部署。机器人端为签名接口模拟器，没有测量物理维修、动作执行或机械安全。第三阶段已验证的签名工具、记录格式和 Solidity 注册合约被复用，链上仍依赖可信桥，不在合约内验证 Ed25519 签名。

## 矩阵与期限参数

| 项目 | 设置 |
| --- | --- |
| 授权策略 | 严格在线验证、固定期限缓存授权、历史 q90 自适应缓存授权 |
| 外部代理延迟 | 每次授权/RPC 请求注入 0 或 50 毫秒响应前延迟 |
| 网络场景 | 始终连接；断网 1.5 秒；断网 4.5 秒 |
| 请求计划 | 每组 5 次场景内请求，再加 1 次恢复/结束探测 |
| 故障检测 | HTTP 心跳请求结束后等待 100 毫秒；单次请求超时 200 毫秒 |
| 固定期限 | 4000 毫秒 |
| 自适应规则 | `min(6000, max(1000, ceil(2*(Q90+250))))` 毫秒 |
| 自适应初始历史 | `[500,500,750,750,500,750,500,500]` 毫秒，因此初始授权为 2000 毫秒 |
| 配额 | 每张离线授权 100 次 |
| 在线策略 | 在线签发 1000 毫秒授权，每次命令再次在线验证同一绑定授权 |

所有组使用新工单和相同初始历史；断网请求计划偏移为断网时长的 0%、20%、40%、60%、80%。相同的是计划，不是墙钟完全一致的到达时间；实测时间全部保留。策略次序按重复轮换，三个重复依次从在线、固定、自适应开始，减少固定顺序影响，但这不能消除全部热身与环境干扰。

秒级 TTL 是机制测试参数。不能把 4 秒结果按倍数换算成 15/30 分钟效果，也不能将本阶段的初始历史解释成实际场站采集数据。第四阶段使用长期合成轨迹研究策略权衡；第五阶段检验真实请求路径和处理成本，二者评估目标不同。

本阶段采用预签授权，命令不等待联网时的周期续签；没有实现第四阶段的半寿命主动续签调度。恢复后再次签发，并把已完整结束的实际断网时长加入历史。旧授权的到期时间保持不变，恢复签发的新授权不会缩短旧授权。

在线场景中客户端在签名之前获取绑定授权，命令抵达网关后再次在线验证该授权；这两个请求分别计入授权样本和逻辑请求数。离线策略在组开始与恢复时签发授权，期限内执行直接使用缓存。线上验证额外成本来自这一明示架构，不能假定所有在线授权架构都具有相同请求数。

## 指标口径

| 指标 | 含义 |
| --- | --- |
| `command_p50_ms` / `command_p95_ms` | 成功命令的网关 HTTP 请求至响应耗时，包含验证、机器人 HTTP 交互、记录签名与 fsync 文件写入 |
| `denied_p50_ms` / `denied_p95_ms` | 被拒绝/失败命令的请求耗时，单独报告 |
| `detection_ms` | 从代理开始切断连接到网关首次失败心跳结束的实测时间 |
| `recovery_detection_ms` | 从代理恢复连接到网关首次成功心跳结束的时间 |
| `flush_ms` | 显式触发补传到全部交易确认和队列文件更新完成的时间，包括授权注册与逐条提交 |
| `restoration_to_flush_ms` | 从外部连接恢复到补传完成，包含检测、恢复签发、探测请求和补传前处理 |
| `authorization_http_requests` | 授权签发/验证请求数，包括超时请求，不含心跳 |
| `offline_accepted` / `offline_commands` | 故障期间计划请求的接受数与请求数 |
| `chain_records` | 该组获得链上记录的数量 |

网关命令响应耗时不含签名前的客户端授权准备，后者在 `authorization_requests.csv` 中另行报告。成功与拒绝耗时不可混合后声称“平均更快”。各组补传记录数不同，补传总时间也不能直接当作同等工作量吞吐量比较；分析时须同时列出链上记录数和注册交易数。

每组只有 6 次请求，p95 往往就是其中最大值，仅为描述性统计。默认每条件 3 次重复也不足以建立稳定的尾延迟结论。先核验机制，再提前固定重复次数并重测，例如 `--repeats 10`；单组参数仍固定。正式论文需说明样本单位、硬件、注入配置和测量范围，不将请求数当作独立设备数。

## 文件与复查

- `runs.json`：全部请求、签发历史、心跳、状态转换、签名记录、机器人签名确认和阶段时间。
- `run_summary.csv`：逐组指标。
- `commands.csv`：每次命令状态和耗时。
- `authorization_requests.csv`：每次授权签发/验证的状态和耗时。
- `summary.json` / `summary.csv`：按延迟、场景、策略分组的跨重复中位数，同时报告有效样本数；是“每组 p95 的中位数”，不是所有请求混池后的 p95。
- `transactions.json`：真实注册与提交交易、回执及事件。
- `public_keys.json`：四种 Ed25519 公钥；私钥只存在运行时内存，没有保存。
- `spool.json`：当前剩余补传队列；正常结束应为空。
- `live_check.json`：原节点退出前的全部回执与记录核对结果。
- `deployment.json` / `contract_artifact.json`：原节点部署地址与合约产物，供解析及新链重放核验。
- `scope.json`：环境、参数、限制；`audit.json`：审计结果；`negative_controls.json`：四项负对照。

审计重新计算请求统计，核对授权期限与自适应历史、三层签名和机器人签名确认、请求/记录数量、序列与哈希链、阶段时间顺序，核对原节点运行时检查记录，并在新链重放全部注册和提交调用、核对事件和条目。负对照故意修改统计结果、签名、历史与回执列表，审计应全部拒绝。审计通过不证明物理维修完成，也不构成形式化安全证明。

## 论文能使用的结论范围

可报告在指定本机环境与注入条件下的真实 HTTP、签名、持久化与本地 EVM 耗时，以及断网期间缓存授权是否继续允许受保护命令。本实验未加入撤销事件，不能据此测量撤销通知或撤销暴露。

这里的 50 毫秒是每个代理请求注入的处理等待，不是采集的真实 WAN RTT；故障时代理等待 350 毫秒返回 503，客户端在 200 毫秒主动超时。网关实际超时与调度延迟均测量，不能预设检测耗时必然等于 200 毫秒。断网起止是控制器的实际时刻，未把定时器目标值当作实际持续时间。

采用系统墙钟作为授权时间，可信时间与回滚防护仍属假设；单进程状态不验证多机并发、崩溃恢复或远程身份部署。本地开发链回执用于检验记录处理流程，不代表公网链最终性。文件系统耗时也依赖操作系统缓存与硬件，不能据此断言断电后必定恢复。此前第二、三阶段的故障证据仍应分别保留。

本阶段未稳定通过当前测试环境下的开发链重启回查，因此明确使用内存节点、运行时原始回执核验和新链重放，不能表述为原链数据库重启持久化通过。网关队列文件仍进行实际落盘。第三阶段独立的故障与持久化结果应分别保留；本包不修改此前上传结果。
