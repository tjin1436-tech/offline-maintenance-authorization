# 开发记录与结果取舍

正式参考结果使用 `reference_results/protocol.json` 中固定的源文件哈希和参数，开发试运行不合并进正式样本。

1. 最初使用WAL与synchronous=FULL。12类故障在线检查通过，但之后独立读取部分工作数据库时，出现数据库与运行时快照不一致。仅报告在线“PASS”不足以接受结果，因此未将这些运行视为正式通过。
2. 增加WAL checkpoint、数据库fsync及关闭握手后，仍观察到归档核对不一致；改为DELETE回滚日志后，直接归档工作文件的问题也没有完全消失。不能根据这些记录断言根因已经定位，更不能据此认定SQLite或Windows本身有问题。
3. 最终采用工作数据库与归档数据库分离：进程关闭前计算状态摘要及文件摘要；父进程等待退出、重新打开实际数据库核对内容；再直接读取文件字节写出归档副本并fsync。没有根据JSON快照重建数据库。后续审计再次逐行核对归档副本，并核对导出事件中的文件摘要。
4. `dev_smoke_06`通过12个故障用例、9项功能检查、6组联网运行、独立审计及5项负对照。随后增加归档摘要核验并固定正式协议。
5. 本次归档问题与此前用户Windows环境的Node长运行异常是两件不同的观察；当前没有证据证明二者同因，也不宣称已修复此前异常。
6. 第一轮全矩阵运行完成36个故障用例、108组性能运行和120秒观察，但独立审计发现追加日志2162笔，与原节点核对2170笔不符。因此该轮未被认定为完整通过，未填补或伪造缺失回执。最终增加在原节点关闭前将控制器实际保留的完整回执数组原子导出为transactions.json，再用同一协议重新运行。追加日志仅作诊断，独立审计以完整导出、原节点重查和数据库交叉核对为依据。

`development_evidence`保留开发轮次的完成状态、过程事件、部分数据库和逐用例证据，供核查失败观察。它不是正式结果。旧开发轮次的源文件哈希对应当时实现，不能用当前版本直接通过源码一致性检查；不要修改这些哈希以让旧结果通过审计。
